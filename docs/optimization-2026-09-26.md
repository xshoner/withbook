# 최적화 검토 — 2026-09-26

기준 커밋: `df19e4e` (main). Next.js 16 / React 19 / Tiptap 편집기, Supabase 저장소, Chromium PDF, HWPX 내보내기 구조를 검토했다.

## 적용한 변경

- 편집기에서 교정 내역, 각주 팝업, 문단·어절 비교를 필요할 때 로드한다. 항상 표시되는 찾기 도구는 기존 즉시 로딩을 유지한다.
- 어절·문단 비교의 LCS 전체 길이 행렬을 두 개의 계산 행과 셀당 1비트 경로로 대체했다. 동점일 때 삭제를 우선하는 기존 규칙과 표시 결과를 유지한다. 시간 복잡도는 여전히 O(n×m)이므로 매우 큰 문서 비교에 대한 무제한 성능 보장은 아니다.
- HWPX에서 동일 assetId의 이미지를 한 번만 내장한다. 각 그림의 개체 ID, 배치 크기, 캡션은 별도로 유지한다. 서로 다른 assetId는 내용이 같더라도 합치지 않는다. 이미지 바이트·해상도·압축 설정은 그대로다.

## 측정

동일 환경에서 변경 전후 `npm run build`를 실행하고 `/projects/[id]`의 client-reference manifest가 가리키는 초기 JS 청크를 중복 없이 합산했다. gzip은 각 청크를 Node 기본 gzip으로 압축한 참고치이며 CDN 실측 전송량과는 다를 수 있다. 공통 런타임 전체 또는 모든 지연 청크의 총량을 뜻하지 않는다.

| 항목 | 변경 전 | 변경 후 | 감소 |
| --- | ---: | ---: | ---: |
| 편집 화면 초기 참조 JS | 640,083 B | 631,589 B | 8,494 B (1.33%) |
| 같은 청크의 gzip 합계 | 202,981 B | 200,160 B | 2,821 B (1.39%) |
| 3,000×3,000 어절 LCS 계산 버퍼 | 18,012,002 B | 1,149,008 B | 93.62% |

계산 버퍼 수치는 구현상 할당되는 typed array 크기다. 원문 토큰, 결과 객체, 브라우저 전체 메모리를 포함하지 않는다. 변경 후 크기는 `ceil(n*m/8) + 2*(m+1)*4`다. 지연 로딩은 다운로드 시점을 옮기므로 모든 기능을 연 경우의 총 JS가 같은 비율로 감소한다는 뜻은 아니다.

HWPX 회귀 테스트에서는 두 자산을 네 번 배치했을 때 내장 이미지가 네 개에서 두 개로 줄어들며, 네 배치의 크기·캡션·고유 ID와 원본 바이트가 보존됨을 확인했다. 실제 파일 절감률은 이미지 반복 사용량에 따라 달라진다.

## 검증과 범위

- 변경 전 테스트 96개 통과, 변경 후 회귀 테스트 포함 99개 통과.
- 프로덕션 빌드 및 TypeScript 검사 통과.
- 이전 구현과 5,000개 무작위 입력의 어절·문단 비교 결과가 완전히 일치했다. 반복 토큰, 빈 입력, 비트 경계, 긴 비교를 확인하는 회귀 테스트도 추가했다.
- 생성한 HWPX를 ZIP CRC 검사와 함께 다시 읽어 이미지 바이트, manifest 참조, 배치 ID·크기·캡션을 확인했다.
- 실제 Edge의 프로덕션 빌드에서 편집기, 지연 로딩 교정 패널, 각주 팝업이 브라우저 오류 없이 동작했다. API는 모의 응답으로 격리했다.
- `SMOKE_DATABASE_URL`이 없어 실제 DB를 사용하는 전체 통합 smoke test는 실행하지 않았다. 한컴오피스에서의 실제 HWPX 열기 및 운영 배포 검증은 이번 검증에 포함하지 않았다.

이미 적용된 WOFF2 글꼴, 백업 ZIP의 이미지 무재압축, 저장소 다운로드 동시성 제한, 일부 대화상자의 지연 로딩은 유지했다. PDF 글꼴·인쇄 규격, 이미지 품질, AI 설정, 원고·버전 보관 정책, DB 스키마는 변경하지 않았다. 운영 저장소 파일 삭제나 데이터 마이그레이션은 수행하지 않았다.
