# 2026-09-25 집필 시간 초과와 복구

## 확인한 사실

- `b0dba0a`에서 앞 문맥을 원문 발췌로 교체하고 입력 예산을 2,500자에서 5,000자로 늘렸다. 단일 집필 범위를 늘리고 인접한 개요 파트를 합쳐 호출하도록 변경했다.
- 보고된 「GPU 봉건제—부는 어디로 모이는가」의 개요 캐시는 04:33:15 UTC에 저장됐다. 배정 분량은 1,100 / 1,400 / 1,400 / 1,168자였다.
- 같은 시점의 개요 호출은 75,612ms에 성공했고, 바로 이어진 본문 호출은 163,969ms 후 `deadline`으로 종료됐다. 개요와 본문이 동일 요청의 240초 예산을 공유하므로 본문에는 약 164초만 남았다.
- 직전 배포 전 최근 본문 파트 호출 9건(04:08~04:30 UTC)은 약 35~74초에 성공했다. 동일 입력 비교 실험은 아니므로 속도 개선율이나 인과관계의 확정 자료로 사용하지 않는다.
- 실패 로그의 토큰 수 0은 종료 usage를 받지 못한 값이다. 실제 사용 토큰이 0이라는 뜻이 아니다. 기존 로그에는 공급자 대기·추론·재시도별 시간이 없어 이를 분리해 확정할 수 없다.

## 판단과 조치

호출 수 감소만을 성능 개선으로 검증한 것이 부족했다. 본문 묶음 확대와 입력 증가가 기존 시간 예산에 적합하다는 근거가 없고, 실제 배포 후 실패가 발생했으므로 해당 최적화 커밋 전체를 되돌렸다. 기존 요약·개요 사전 준비 및 단계별 시간 측정은 유지한다. 별도 다중 집필·교정 변경, 모델·API 설정, 저장 원고는 수정하지 않는다.

복구는 이전 동작으로의 회귀이며 공급자의 응답 시간이나 모든 긴 집필의 성공을 보장하지 않는다. 다시 최적화할 때는 같은 원고·설정의 개요 시간, 첫 본문 시간, 전체 시간, 완료율과 분량·내용 누락을 비교해야 한다. 모의 AI 테스트의 호출 횟수만으로 실제 속도·품질 개선을 주장하지 않는다.
