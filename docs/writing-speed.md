# 집필 준비 시간 단축

## 필요한 앞 내용만 준비

같은 장의 직전 절부터 거슬러 올라가고, 남는 범위에 이전 장 요약을 넣는다. 2,500자 예산이 차면 더 오래된 장·절 요약을 호출하지 않는다. 완성된 프롬프트는 책 순서로 정렬된다. 가까운 요약 하나가 예산보다 길어도 빈 문맥이 되지 않도록 잘라서 포함한다.

절·장 요약은 본문/절 요약 해시로 재사용하며 같은 서버 프로세스의 중복 요청을 공유한다. 요약 중 원고가 바뀌면 이전 본문의 결과로 캐시를 덮어쓰지 않는다.

## 편집 중 미리 준비

- 본문 자동 저장 성공 후 20초간 변경이 없으면 해당 절을 요약한다. 다시 입력하면 대기를 취소하고 다음 저장 후 재예약한다. 저장 실패·미저장 원고에는 준비 요청을 보내지 않는다.
- AI 집필 완료·새 버전 채택 후에는 저장된 원고 요약을 바로 예약한다.
- 그 장의 모든 절 요약이 최신일 때만 장 요약까지 준비한다. 준비 작업이 다른 미작성 요약을 한꺼번에 생성하지 않는다.
- AI 옵션을 열고, 5쪽 초과 목표와 스케치가 있으며, 저장이 완료되었으면 20초 후 새로 쓰기용 개요를 준비한다. 준비 과정은 원고와 버전을 만들거나 변경하지 않는다.
- 브라우저에서 예약된 준비 작업은 하나씩 실행한다. 탭을 닫으면 아직 시작하지 않은 예약은 사라지며 실제 집필 시 필요한 내용을 정상적으로 준비한다.

## 개요 재사용

`AppSetting`의 `ai:outline-cache:<sectionId>`에 절당 최근 개요 하나를 보관한다. 유효 기간은 24시간이며 만료된 값은 재사용하지 않는다. 새로 준비하면 같은 행을 교체하고, 만료된 행은 프로젝트 목록의 일일 정리 때 삭제한다. 스키마 변경은 없다.

렌더링된 전체 프롬프트와 개요 모델의 제공자·주소·모델·추론 강도·출력 한도를 SHA-256으로 비교한다. 분량, 스케치, 추가 지시, 앞뒤 내용, 책 정보, 문체, 프롬프트 규칙이 바뀌면 재생성한다. 이어쓰기는 기존 본문을 포함한 프롬프트가 달라 새로 쓰기 개요를 재사용하지 않는다. 키 원문은 캐시에 들어가지 않는다.

## 시간 측정

AI 옵션의 **최근 집필**을 펼치면 원고 조회, 앞 내용 정리, 개요 준비, 본문 생성 시간을 확인한다. 첫 본문 시간에는 소제목을 제외하고 모델이 실제 본문을 처음 반환한 시점을 사용한다. 본문 생성 시간은 모델의 첫 응답 대기와 여러 파트 사이 대기를 포함한다. 총 시간은 서버 집필 함수의 시작부터 완료까지이며, 브라우저 네트워크·완료 후 원고 저장 시간은 포함하지 않는다.

현재 탭의 최근 결과를 절별로 최대 100개 보관한다. 서버에는 `[write-timing]` 구조화 로그로 완료·오류·중단과 단계별 시간을 남긴다. 로그에 프롬프트·원고·API 키는 포함하지 않는다.

검증: `npm test`, `npm run typecheck`, `npm run build`. 실제 시간 개선 폭은 같은 분량·모델에서 캐시가 없는 첫 집필과 준비가 끝난 집필을 비교해 확인한다.

## 2026-09-25 측정과 결정 (같은 원고·같은 설정 비교)

모든 AI 호출은 서버 로그에 `[ai-call]` 한 줄을 남긴다: 용도, 모델, 전체 시간, 첫 글자까지 시간(`firstTextMs`), 입력·출력·추론·캐시 토큰. 프롬프트·원고·키는 넣지 않는다.

### 추론 강도 — 본문 집필에는 적용하지 않음
3쪽 절 하나를 새 버전 모드로 두 번씩 집필했다(입력 17,124토큰 동일).

| 설정 | 첫 글자 | 전체 | 출력 토큰 |
|---|---|---|---|
| 기본 | 79s / 113s | 99s / 138s | 5,879 / 8,102 |
| `reasoning_effort=low` | 16s / 61s | 62s / 85s | 2,652 / 4,853 |

게이트웨이는 `reasoning_tokens`를 0으로 보고하지만 첫 글자 전 대기가 길어 생각 토큰이 출력 토큰에 섞여 있다. 블라인드 쌍대 비교(4쌍 × 순서 바꿔 2회, 기준: 문체 프로필·스케치 반영·흐름·문장·독자)에서 **기본 5승, low 2승, 1무**였고 판정 이유는 대부분 low의 문체 밀도(작가 고유 표현·리듬·수사의문) 저하였다. 품질을 유지하기 위해 본문 집필의 추론 강도는 바꾸지 않는다. 용도별 연결 설정의 추론 강도는 이제 게이트웨이에도 전달된다(기본값이면 보내지 않음). 측정용으로 `AI_REASONING_OVERRIDE="section_write=low"`를 서버 환경변수로 줄 수 있다(운영에는 두지 않는다). `thinking: {type:"disabled"}`는 게이트웨이가 400으로 거부한다.

### 프롬프트 캐시 — 적용
게이트웨이 Claude 모델에서 system 메시지에 `cache_control: {type:"ephemeral"}`을 달면 5분 안의 다음 호출이 캐시를 읽는다(`cached_tokens`). 8쪽 절 실측: 2~4번째 파트가 입력 17.9k 중 15.1k를 캐시에서 읽었고, 파트 첫 글자 시간은 1번 49.5s → 2~4번 20.9 / 16.0 / 10.9s였다(생각 시간 차이가 섞여 있어 캐시만의 효과로 단정하지 않는다). 출력 내용은 캐시와 무관하다.

### 긴 절 자동 이어 쓰기 — 적용
한 요청의 시간 한도(파트 시작 150초)로 멈추면 서버가 `resume`(다음 파트 번호·개요)을 보내고, 브라우저가 같은 개요와 지금까지 쓴 글로 다음 요청을 보낸다(최대 8회). 파트 프롬프트는 한 번에 쓸 때와 같다. 실측: 8쪽 절이 2회 요청, 263초에 4파트 모두 완료, 5,562자(목표 5,600). 이전에는 2파트 뒤 멈추고 [이어쓰기]를 눌러야 했다. 이어 쓰는 요청은 `ai_write` 버전을 다시 남기지 않는다.

### 개요 프롬프트
개요 요청 마지막 줄이 "본문만 출력하라"로 system의 "JSON만 출력"과 충돌해 형식 오류·재호출 위험이 있어, "개요 JSON 하나만 출력"으로 바꿨다. instruction.md는 소제목 규칙 때문에 그대로 둔다.

### 체감
집필 창에 첫 문장 전 경과 초를 보여 준다(실측 첫 문장까지 1~2분). 집필·교정은 백그라운드로 돌므로 그동안 다른 절을 편집할 수 있다.
